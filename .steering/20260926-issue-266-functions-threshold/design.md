# v8 functions 閾値の下振れバッファを外す (#266)

## 結論

`src/lib/**` の functions 閾値を 75 から 80 に上げ、branches / lines / statements と同じ 80 に揃えます。`src/services/**` の 85 は据え置きます。
#113 で観測された「CI だけ functions が 12〜13pt 下振れする」現象は、main の直近 8 run（異なる SHA、Node v24.20.0）で一度も起きていません。ローカル（Node v24.9.0）の実測とも per-file で完全に一致しました。そのため、下振れを前提にした説明コメントも実測に合わせて書き換えます。

## 観測（main の CI 8 run とローカル）

| 対象 | 実測 functions | 1 関数あたりの重み | 現閾値 → 新閾値 |
|---|---|---|---|
| `src/services/**` | 35/39 = 89.74% | 約 2.6pt | 85 → 85（据え置き） |
| `src/lib/**` | 39/46 = 84.78% | 約 2.2pt | 75 → 80 |

- 対象 run は 35480462509〜35559605981 の 8 件です（`b7d54a0` 時点で lib 36/43 = 83.72%）。run 間で差が出たのは、81fc07b のファイル移動（`src/lib/cache` → `src/services/cache`）による 1 行だけでした。
- 上の表の値は、#276 のマージ後の `e49646c` をローカルで計測したものです。lib の関数が 3 つ増えましたが、どれもカバーされています。
- Issue に書かれていた「lib 88.88%」は `src/lib/http` のディレクトリ行の値で、`src/lib/**` 全体の集計ではありませんでした。
- `src/lib` で未カバーの 7 関数のうち 6 関数は `src/lib/supabase/*` のクライアント生成関数です。unit テストでは Supabase をモックしているので、構造的に呼ばれません。残る 1 関数は `safe-fetch.ts` の無名関数です。
- 新閾値 80 のもとでは、テストのない関数が 2 つ追加されても通り（39/48 = 81.25%）、3 つ追加されると落ちます（39/49 = 79.59%）。services の 85 も同じで、2 つまでは通り（35/41 = 85.37%）、3 つで落ちます（35/42 = 83.33%）。どちらも、新しい未テスト関数の追加を実際に検出できる幅です。

## 検討した代替案

| 案 | 却下理由 |
|---|---|
| lib を 83 など実測ぎりぎりまで上げる | テストのない関数が 1 つ追加されるだけで落ちます（39/47 = 82.98%）。Node の更新で 1 関数ぶん揺れた場合の余地もありません |
| services を 88 に上げる | テストのない関数が 1 つ追加されるだけで落ちます（35/40 = 87.5%）。Issue も据え置き可としています |
| 数 run 追加で観測してから判断する | 8 run・異なる SHA・ローカルとの一致で十分です。再発した場合は CI が落ちて気づけます |
| 現状維持（75 のまま） | テストのない関数が 7 つ追加されるまで検出できず、ゲートとして機能しません |

## Non-goals

- `src/lib/supabase/*` を unit テストでカバーすること（e2e が担保しています）
- branches / lines / statements、`app/api/**`、`components/**` の閾値の見直し
- Node のパッチバージョンを CI で固定すること
